# 架构决策记录（ADR）

记录**为什么**这样选。这类理由最容易随时间丢失，而它们恰恰是最难重新推导的。
每条都附上当时的实测数据 —— 没有数据的决策在未来很容易被盲目推翻。

---

## ADR-001：sidecar 用 PyInstaller onedir，不用 onefile

**背景**：后端要打包成单个 exe 随应用分发（Tauri 的 `externalBin` 要求单文件）。

**实测对比**：

| | onefile | onedir（采用） |
|---|---|---|
| 启动到接口可用 | 2.5 – 2.8s | **0.65 – 0.69s** |
| `%TEMP%` 临时目录 | 1 个（约 40MB） | **0 个** |
| 进程数 | 2（引导进程 + Python 子进程） | **1** |

**决策**：onedir。

**理由**：
1. onefile 每次运行都要把压缩载荷解压到 `%TEMP%\_MEIxxxxxx`。
2. 它是父子双进程，`child.kill()` 只杀得掉父引导进程，Python 子进程会变成孤儿
   并残留 `_MEI` 目录 —— 这个 bug 真实发生过（见 ADR-003）。
3. 「运行时自解压到临时目录」正是恶意软件 dropper 的典型行为，是 Defender
   把本程序误报为 `Trojan:Win32/Wacatac.B!ml` 的**主要特征**。
4. 长期看，持续写 `%TEMP%` 对 SSD 寿命也是无谓损耗。

**如何绕开 Tauri 的单文件约束**：仍产出那个单文件占位 exe 供 `tauri build`
校验；真正的便携包由 `release.yml` / `build_sidecar.bat` **手工组装** ——
把 `backend.exe` 与 `_internal\` 平铺到同一目录即可（onedir 的 exe 正是从
**自身所在目录**的 `_internal` 找依赖）。

**验证方式**：把 `_internal` 移走后确实启动失败，证明它真在被使用。

## ADR-002：应用数据目录由外壳注入，后端只认环境变量

**背景**：历史、日志、端口文件需要在程序目录之外（Program Files 只读），
但便携包又希望「解压到哪、数据就跟到哪」。

**早期做法**：`%APPDATA%\TextForge` 在 4 个 Python 模块里各自拼接，
**Rust 外壳侧还把同一套逻辑又抄了一遍**。

**问题**：两侧一旦不一致，前端就永远读不到 `port.json`，表现为「一直连不上后端」。

**决策**：新增 `backend/utils/appdir.py` 作为唯一数据源，优先级

```
TEXTFORGE_DATA_DIR（外壳注入） > exe 旁的 data/ > %APPDATA%\TextForge
```

外壳解析后经**环境变量**注入 sidecar；后端只认这个变量，认不到才回退。

**要点**：默认仍是 `%APPDATA%`（不靠「猜测 exe 目录是否可写」），否则单元测试
会把数据写进 `venv/Scripts`，彻底搞乱测试隔离。

## ADR-003：本地 API 必须鉴权

**背景**：后端绑 `127.0.0.1` + 随机端口。此前**没有任何调用方验证**。

**风险**：任何本地进程读一下 `data/port.json` 就能直接调接口 ——
`/api/start` 可指定任意 `input_path` / `output_path`，以当前用户权限读写磁盘任意位置；
`/api/system/open` 可 `os.startfile` 打开任意路径。
浏览器里任意网页也可能打过来（`text/plain` 这类简单请求不触发 CORS 预检，
请求会照常执行，只是读不到响应）。

**决策**：外壳用 CSPRNG 生成 token，经环境变量注入 sidecar，前端只经 Tauri IPC 取得。

**关键点：token 从不落盘。** 落盘等于公开 —— 任何本地进程都读得到 `port.json`。
存在进程内存 + 子进程环境变量里。

**实现注意**：
- 中间件用**纯 ASGI**，不能用 `BaseHTTPMiddleware` —— 后者会缓冲响应体，
  直接破坏 SSE 长连接（`/api/events`）。
- `/api/health` 豁免（不返回任何数据，供探活）。
- 未配置 token 时放行，否则单元测试与 e2e 会被 401 拦死；生产路径上外壳必定注入。
- **外壳自己发起的 HTTP 调用也必须带 token**。曾漏带导致关窗时的 `/api/stop`
  与 `/api/system/shutdown` 被 401 静默拒绝，优雅退出退化成强杀，
  ADR-001 里修掉的孤儿进程问题原样回归。且这条路径 e2e 覆盖不到
  （e2e 直接起 `python main.py`，不经外壳、不注入 token）。

## ADR-004：心跳只写内存，不落盘

**背景**：原先心跳每 15s 把**整个** `progress.json` 读出来、改一个字段、
再全量写回 + fsync。

**问题**：`progress.json` 在缝合阶段可达数十 MB（锚点内嵌全文）。
长时段运行下，每 15s 一次全量重写就是实打实的写放大，
同时还要每 15s 解析 + 序列化几十 MB JSON。

**决策**：心跳时间戳改为只维护 `state.last_heartbeat`（内存），
`/api/status` 优先返回内存值。

**理由**：`last_heartbeat` 的唯一用途是前端判断「是否僵死」
（`pipeline_running` 且心跳超 90s 报警），**不参与任何恢复决策**，因此完全不必落盘。
界面拿到的是内存值，反而更准（没有 fsync 延迟）。

**实测**：e2e 场景写入量 863KB → 406KB；真实长跑场景下这部分归零。

## ADR-005：闸门标志的 clear 必须早于阶段落盘

**背景**：蓝图门与验收门原先都是：

```python
progress['current_phase'] = 'phase2_waiting'
atomic_write_json(progress_path, progress)   # 此刻界面已弹框、resume 已就绪
state.blueprint_confirmed.clear()            # 把刚到的确认抹掉
```

**问题**：存在一个窗口 —— progress 已是闸门阶段（界面弹框、`/api/status` 的
resume 已就绪），而标志还没 clear。此刻到达的确认会被紧接着的 `clear()`
**静默丢弃**：流水线随后永远等不到，界面却显示「已确认」，**无任何报错**。
刷新后由 resume 路径弹出的弹窗正好走这个窗口，所以这是真实产品缺陷。

**决策**：先 `clear()` 标志，再落盘阶段。这样「闸门可见」之后到达的任何确认
都不会再被清掉。qc 门本来就是先 clear 再等，无需改动。

## ADR-006：免安装便携 zip，不再发 NSIS 安装包

**背景**：v0.4.0 的 NSIS 安装包被 Defender 隔离并删除。

**诊断**：威胁名 `Trojan:Win32/Wacatac.B!ml` —— 末尾 `!ml` 表示**机器学习泛化判定**，
不是病毒特征码命中，属误报。

**定位元凶**：实测把 25MB 的 PyInstaller sidecar 单独扫是**干净**的；
NSIS 把这份高熵载荷再包一层，触发启发式评分。

**决策**：`bundle.active=false`，发布手工组装的便携 zip。
无安装壳、无注册表、无 Program Files 写入。

**未做的**：代码签名。没有数字签名意味着 Defender 仍可能误报，
SmartScreen 也无法消除。根治需要 EV 证书或 Azure Trusted Signing（开源项目免费）。
ADR-001 去掉自解压后误报概率已大幅降低，但不是零。

## ADR-007：测试用「单一全局闸门驱动」

**背景**：e2e 要像真实用户一样点掉所有人工闸门。最初每个场景各起一个驱动线程。

**问题**：所有驱动轮询**同一个后端**，彼此看不见对方在干什么，导致两类反复出现的
偶发失败：

1. 旧场景的驱动替新场景确认了闸门 —— 场景七「重拆未生效，拆书预览已被确认」，
   流水线提前冲进 phase1。
2. 去重键跨 run 复用 —— 上一轮记下的 `blueprint_ready` 把下一轮的蓝图闸门
   当成已处理而跳过，流水线无限卡在 `phase2_waiting`。

**决策**：改为**单一全局驱动**，以 `/api/status` 的 `run_id` 划分轮次，
换 run 即清空去重状态（且必须在处理事件流**之前**完成，否则新 run 的闸门事件
会拿上一轮的记录比对而被跳过）。

**另一条纪律**：确认闸门时**不要带 `run_id`**。`_check_run_id` 只在「传了且不匹配」
时拒绝，而 `/api/status` 的 `run_id` 与 `current_phase` 都来自定期落盘的
`progress.json`，在闸门处会滞后 —— 带着滞后的 id 去确认会被 409 静默吞掉。
后端同一时刻只可能有一个 run，交给它用 `state.current_run_id` 判定即可。

## ADR-008：连续性、内容级质检与有界并发

**背景**：v0.11.0 解决了长书蓝图与成品可核查性，但重构仍按批独立进行：
下一批看不到上一批结尾，坏批次要等成品出来才发现，批次只能串行。

**决策**：

1. **跨批连续性**：phase3 在提示词中注入上一批结尾片段（约 600 字，按 token
   预留预算）。优先取该章**重构稿**（文风最连续）；并发时同波次前批可能还没
   写完，自动退回取该章**原文**，保证不空等也不跳过衔接。片段只用于衔接，
   明确要求模型不复述、不续写。
2. **内容级质检 + 自动重写**：批次落盘前检查空章、塌缩/膨胀、占位、机器标记、
   重复章、禁用设定命中。命中 `bad` 时把问题清单作为追加消息重发一次（温度
   降到 ≤0.5），保留问题更少的一版；每批最多一次、整轮最多 3 次。重写失败
   不报废批次，保留首次合格输出，遗留问题写入进度与最终质量报告。
3. **有界并发**：`max_concurrency` 默认 1（串行），可选 1-4。按波次 `gather`，
   拆分结果回队到下一波；进度在波次结束后串行落盘。逐章验收开启时强制串行。
   并发只用于 phase3：phase1 依赖上一批诊断摘要作为重叠上下文，天然串行。

**为什么不做默认并发**：本地小模型/小显存并发请求容易 OOM；云端限流也更敏感。
默认保持旧行为，把选择权交给用户。

**代价**：自动重写可能让单个坏批次多花一次调用；连续性片段占用约 200-600 token
预算，已从单批正文上限中预先扣除。

## ADR-009：缝合降级、前情摘要与富文本 docx

**背景**：v0.12.0 之前有三处「用户看得见但拿不到」的缺口：

1. 缝合的标记契约校验写在 `call_with_retry` **之后**，模型少打一个
   `===PREV_END===` 就直接抛错终止整轮 —— 此时全部重构稿已经产出，却因为一次
   交界润色失败而报废。
2. `_record_anchors` 分两轮循环判重，第二轮的 `known` 已被第一轮补齐，
   `new_keys` 恒为空：`stitch_anchors.jsonl` 从未写入过完整锚点，
   缝合报告只能退回不含原文/替换文的轻量引用。
3. 前端「docx富文本」开关传到后端后无人消费，勾与不勾输出完全一样。

**决策**：

1. **缝合契约进重试 + 失败降级**：标记解析与「替换段不得远短于原文」的长度校验
   放进 `validate`，失败时带错因重试一次（温度 ≤0.4）；仍失败则跳过该交界、
   记入 `progress.stitch_failures`，成品照常产出，并在质量报告与质检导出门里
   显式列出。提示词同时改成「必须完整返回两整段」，从源头减少只回过渡句的情况。
2. **前情摘要注入**：重构提示词除上一批结尾外，再带上一批诊断摘要（章节剧情 +
   人物状态，去掉断层建议与 JSON）。它与结尾片段互补：结尾管**文风衔接**，
   摘要管**事实一致**。按 token 单独预留预算（180-500），批内章节重叠的
   兄弟批次（拆批产生）不参与选取，避免把当前章内容当「前情」剧透给模型。
3. **富文本 docx**：`rich_text` 真正生效 —— 章标题（Markdown `#` 或「第N章」
   等中文标题行）升为 Word 标题样式，章与章之间分页，`**粗体**`/`*斜体*` 渲染
   为对应 run。默认关闭，关闭时逐字节沿用旧的 `---` 分隔排版。

**为什么缝合失败选择降级而不是终止**：缝合是可选润色，重构稿才是主体。
一次交界失败丢掉整本书的代价，远大于「这处交界没润色」；而降级路径会把
失败点写进质量报告，用户能定位到具体交界，不存在静默丢失。

**代价**：前情摘要再占 180-500 token 预算，单批正文上限相应略降；
缝合降级可能让个别交界保持原样（已在报告中列出，可人工补）。

## ADR-010：缝合面积封顶、代价前置与质检结论同步

**背景**：把整条流水线按「模型真实会怎么做」重算一遍后，暴露出四个只有拿真产物
才能发现的口子（前三条各自独立成立，第四条是审查改动方案时发现的）：

1. 缝合窗口是 `context_window × 1.5 × 0.075`，随用户填的上下文**线性放大**。
   128k 窗口下算出 14745 字 —— 比一整章还长，「修补交界处」于是变成「整段替换整章」，
   而唯一的护栏是替换段长度比 0.5~3.0，整段重写恰好能通过。
2. 诊断阶段的 `max_tokens` 写死 2000，而结构化断层 JSON 追加在输出**末尾**：
   批一大就先截掉 JSON，`fix_list` 拿到空清单，日志里只有一行 warning ——
   用户勾了「修断层」却毫不知情。
3. 连续性片段按 **600 字符**裁剪，而预算按 **token** 预留（8000 窗口只留 320 token），
   注入的片段可以超出预留近一倍，把正文挤瘦。
4. 单章重生成（`/api/regen_chapter`）覆盖重构稿后不重跑内容级质检：`batch_qc`
   继续保留旧结论 —— 已经改好的章仍被报告指控，新引入的占位/塌缩又没人记录。

**决策**：

1. **窗口封顶 1200 字 + 最小改动闸门**：交界窗口取 `min(线性值, 1200)`；
   新增闸门 `stitch_minimal_change`（默认开），用分句对照的改动率
   （原文句子没被原样保留的比例）>35% 判为整段重写，走「带错因重试一次 →
   仍不合格则保留原文交界」这条既有降级路径，并记入质量报告。
   被拒原因是「改动过大」时，重试提示改成「原句逐字照抄、只在交界新增过渡」，
   而不是继续叮嘱「完整返回两整段」。
2. **诊断预算随批规模缩放并把丢失变可见**：`budget.diagnose_max_tokens(n, with_json)`
   = `min(4000, 600 + 260n + (900 if with_json))`；JSON 解析失败改为发
   `sse_emit("error", {kind:"warning", code:"diag_json_missing"})`，同时进进度与报告。
3. **一律按 token 裁剪**：连续性片段与前情摘要都改为按 `estimate_tokens` 收，
   预留值仍来自 `continuity_token_allowance` / `story_memo_token_allowance`；
   删掉 `CONTINUITY_CHARS`。前情摘要保**头部**（先说剧情），衔接片段保**尾部**。
4. **默认上下文 8000 → 32768，且不提供 128k 档预设**（`src/presets.ts`）：
   按 `core/estimate.py` 的算式推算，60 章的书在 8000 下切 30 批、脚手架占输入 68%，
   32768 下 8 批（撞上单批 8 章上限）、占 42%；再放大窗口批数不再下降，
   而蓝图/前情/衔接的预留继续随窗口增长，128k 反而多花约 39% token。
   这条判据由 `tests/test_estimate.py` 的拐点用例与 `src/presets.test.ts` 共同守着。
5. **开跑前预估与花费前置**：`POST /api/estimate` 复用真跑的同一组算式
   （`body_token_budget` + `pack_groups` + `diagnose_max_tokens` + 缝合窗口上限），
   前端与 `/api/start` 共用 `buildStartBody()`，单价只在前端折算、不上传。
   预估不含自动重写与拆批重跑，因此是**下界**，界面按原样显示这句话。
6. **重写即刷新结论，并并回内存**：`_refresh_qc_after_regen` 只替换属于该章的
   `batch_qc` 条目（同批其他章的结论原样保留），同步重算派生物
   `pre_stitch_issues`；验收门的吸收清单扩为 `ACCEPT_ABSORB_KEYS`
   （`accepted_batches` + `batch_qc` + `pre_stitch_issues`）。
7. **窗口派生系数与结构判据只有一个来源**：`context_window × 1.5` 这个换算率原本在
   splitter / refactor / blueprint / control / estimate 各写一份，现在统一为
   `window_char_capacity()`；章数上限、重叠比例、缝合窗口、蓝图三档长度
   （生成 / 上下文总预算 / 确认接口接受上限）、分卷压缩的块预算与输出目标与轮数
   上限（`blueprint.MAP_*`）、以及 phase0 的两条结构判据（兜底段长、空章门槛）
   也都只有一处定义。
   防线分两层，都在 `tests/test_budget_source.py`：字符串门禁拦住「把字面量抄回来」，
   **行为门禁**逐个 monkeypatch 源头常数、要求预估侧跟着变 —— 后者才拦得住
   `int(budget * 0.4)` 这种换了写法的拷贝（变异验证 7 次：改回任一处本地算式，用例即红）。
   顺带修掉两处真实错配 ——
   ① 确认接口按 `chars × 0.20` 而生成上限按 `blueprint_chars()` 各算一份，窗口小于约
   6667 时**接受上限低于生成上限**，用户在闸门里原样点确认会被自己 422 拒掉；
   `blueprint_accept_max_chars()` 取两者最大值收口，行为只在原本会违规的小窗口上变化
   （变大不变小，不会新增拒绝）。
   ② `compress_summaries(max_rounds=MAX_COMPRESS_ROUNDS)` 这种写法会把常数**固化进
   默认参数**（import 时求值），改源头只动得到预估那一边；改成 `max_rounds=None`
   再在函数体里取常量。这条是行为门禁实测出来的，不是读代码读出来的。
   ③ 预估的分卷压缩调用数原先按「总量 ÷ 平均块长」估块数，把真跑**原样保留、不调模型**
   的单条块也算成一次调用，于是比真跑多算 —— 与「预估是下界」这句话相反。现在预估直接
   调用真跑的 `chunk_by_budget` 分块并照抄单条块规则，`test_predicted_map_calls_equal_the_real_run`
   逐次比对调用数与输出上限之和（语料里特意放了一条超长摘要来触发单条块）。
8. **质量报告生成失败必须留下原因（v0.13.0 发布当天的 CI 事故）**：finalize 里那层
   `try/except` 原先把报告生成失败收成一行 `logger.warning` —— 成品照常交付，但
   界面只显示「尚无报告」，CI 里也只拿到一个 404。现在失败原因写进
   `progress["quality_report"] = {status: "failed", error: ...}`，`/api/output/quality`
   在 404 详情里把它带出来；端到端读报告改为「拿不到就判 FAIL 并打印原因」，
   而不是抛 HTTPError 把后面所有场景一起带走。成品交付语义不变（报告仍是诊断产物）。

**为什么最小改动闸门默认开（打破「门默认关 = 旧行为」的约定）**：闸门拒绝后的
降级结果恰好就是旧路径下「缝合失败」的行为 —— 保留原文交界。误判的代价只是
「这处交界没润色」，漏判的代价是「一整章被悄悄换掉且长度比看不出来」，
两个方向的代价不对称，所以把默认值放在安全的一侧。

**阈值是设计取值，不是实测值**：35%（拒绝）与 25%（报告提醒）都还没有真机分布支撑。
25% 必须低于 35% —— 闸门开着时每个已应用补丁的改动率都不可能越过 35%，
提醒阈值若设在 0.5 就永远不会触发，等于把这条信号写死（已有用例断言这个大小关系）。
真实分布要等拿真模型跑一轮之后再定档。

**代价**：窗口封顶让模型写过渡时看到的上下文变少（1200 字/侧对交界足够）；
闸门会让个别本来能落地的补丁被拒绝，成品相应保持原文（报告与日志都列得出来）；
默认窗口调大后，本地小模型用户需要显式选「快速低保真」，填大了由
「上下文超限自动拆批」兜底、不会报废整轮；单章重生成多付一次纯本地的
质检计算（不调模型）。
